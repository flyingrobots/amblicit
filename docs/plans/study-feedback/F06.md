## 2. Problem Description

The JSON authoring API supports custom types and target adapters. The guide does not show a causal-cell executable recipe. Authors change the fixture generator instead.

## 2b. Proposed Solution

Provide an application-owned `edict.lawpack-authoring/v1` JSON definition through `edict.lawpack-build/v1`. Add a runnable how-to and public binary witness.
Use an application helper to derive all type limits, byte caps, budgets, and witness types from explicit inputs. This helper does not add compiler-level lawpack parameters.
For text, distinguish scalar maxima from physical UTF-8 byte caps. Show stock and 4 KiB byte-cap variants. Give the selected provider package identity and compatible schema/version. Verify both variants through actual authoring and application build.

## 2c. Alternatives considered and rejected

Compiler-level lawpack parameterization: the existing JSON API already supports owned definitions.
Change generator literals per application: this changes shared fixture authority and duplicates derived limits.
Treat scalar maxima as byte caps: non-ASCII input invalidates the size contract.

## 2d. Acceptance Criteria

Author and compile stock and larger-value variants through public JSONL operations. Do not modify the stock generator to vary application bounds. Check canonical identities and parameter consistency. State that compilation alone does not prove runtime execution.

## 2e. Test Plan

Golden: public authoring then application build. Edges: changed key/value maxima, UTF-8 expansion, output budget too small, and configuration/type disagreement. Known failure modes: unsynchronized limits. Fuzz and stress: none; two finite parameter sets suffice.

### Budget calculation boundary

The preparation helper in
`crates/edict-cli/examples/configurable_causal_cell/limits.rs` computes the exact
maximum canonical CBOR size of the proposed `{ key, value }` result, including
map, field-name and text headers and four UTF-8 bytes per scalar. Its tests use
the public encoder on maximum Unicode strings as an independent oracle, including
CBOR header transitions. The physical write ceiling adds the selected create
profile's 64-byte overhead to the explicit replacement cap.

The allocation reservation sums the maximum input encoding (including a
128-scalar `basis`), output encoding and replacement cap. This is an explicit
example budget choice, not a proof of all runtime allocations. Zero parameters,
scalar-to-byte inconsistencies and checked-arithmetic overflow have distinct
errors. JSON document generation and repeatable public lawpack authoring are now
implemented by the example support modules and their integration tests. The
standalone command, public application builds and runnable guide are now
present. The real pinned provider accepts both variants and stale pins or
undersized output budgets reject while preserving existing output. Additional
provider-substitution evidence and review remain open.

### Configuration refusal witnesses

The real-provider test also reauthors and repins two invalid configurations for
each variant and directory. A zero replacement cap is refused with
`InvalidProviderInvocation` at provider-schema admission; an aliased key and
replacement field is refused with `ProviderLowererRefused`. Both preserve the
previous executable package and verification report. These are characterization
checks of existing behavior, not a new RED/GREEN implementation cycle. The first
run incorrectly expected the zero cap to reach the lowerer; the observed schema
refusal corrected that oracle.

These witnesses do not prove the broader scalar/type-to-byte-cap consistency
claim in LAUTH-TP-020. That item remains planned. The helper enforces its own
parameter relationship; provider acceptance alone must not be described as
general parameter consistency or runtime ingress validation.

### Corrected parameter-consistency boundary

The original LAUTH-TP-020 wording assumed the pinned v1 provider would refuse
all substituted inconsistent metadata. An executable counterexample contradicts
that assumption: after public reauthoring and source repinning, replacing the
physical cap with one byte still produces a successfully verified application
package while retaining the wider value type. The first refusal-hypothesis run
failed because application build exited zero. This is a characterization result,
not a new compiler defect proven by the experiment. No oversized value was
executed.

F06's accepted scope is an application-owned helper and recipe, not a new Echo
validation contract. Preserve the original parameter-consistency outcome by
enforcing it at helper generation, testing maximum UTF-8 encodings and typed
helper refusal, and documenting the provider's separate byte-cap contract. The
provider witness must retain both real invalid-configuration refusals and this
accepted independent-cap case; it must inspect the emitted one-byte program cap
and restore the original package/report exactly. This replaces the unsupported
blanket-provider-refusal assumption with explicit evidence, without dropping
configuration/type-disagreement coverage.

General provider schema consistency, runtime ingress validation and verifier
mutation testing are not established by these witnesses. The first two remain
separate runtime/provider concerns; F06 introduces neither capability. Review
must assess this correction alongside the original study item 6 and issue scope.
