Why make another language?

A conventional function signature usually says little about authority. An operation called updateDocument might inherit all the privileges of its process.

Edict makes more of that contract explicit. The operation states its dependencies, constraints, effects, and limits. The destination keeps control of admission.

This matters when the operation author and the host have different responsibilities—especially when an agent proposes changes.

Who made it, and when?

James Ross, under flyingrobots, initiated the repository on 17 June 2026. The first compiler spine followed on 21 June.

Hello Echo's compiler and durable execution examples entered history in July 2026. These are development milestones, not evidence of broad production adoption.

The original rationale places Edict between application contracts, Continuum's protocol concepts, and a runtime such as Echo.

Where would I use it?

Consider Edict for restricted extensions, agent-authored operations, editor commands, or automation that needs explicit authority and attributable outcomes.

It is a domain-specific language. It does not replace the host application, user interface, operating system, or arbitrary scripting environment.

Developers who know capability security, effect systems, or transaction processing will recognize the problem. A project that needs unrestricted libraries immediately may find the current subset too narrow.

What does the compiler actually prove?

It checks supported types, bounds, effects, and constraints. A read-only profile cannot accept a write-class effect.

For supported unsigned subtraction, an input condition such as lower <= upper can establish that upper - lower cannot underflow.

That is a conditional guarantee. The runtime must check the actual input condition. Edict does not infer every cost or prove arbitrary mathematical properties.

What are Core IR, lawpacks, and target profiles?

Core IR is an intermediate representation of operation meaning. It retains types, dependencies, constraints, budgets, and results.

A lawpack supplies technical rules and operation contracts. An exact digest identifies the selected content. “Law” here means technical rules.

A target profile describes the destination's supported interpretation. Target IR records that interpretation. A target can reject meaning it cannot support.

How does it touch the outside world?

Through explicit requests and authorized adapters. Edict describes the request. Echo coordinates it. The adapter receives only its permitted external authority.

Hello Echo includes workspace observation and validated patch examples. Their recovery rules preserve ambiguous outcomes instead of inventing success after a crash.

Pure evaluation and private bounded reads do not automatically produce durable history or receipts. See the external-action examples ↗

What is new? What came before?

The ingredients have substantial prior art. Edict's distinctive work is their composition around explicit operations, target interpretation, and destination-owned admission.

  • Proof-carrying code: a consumer checks evidence against its safety policy.
  • Dafny and F*: specifications and proofs about programs.
  • Koka: effects as part of a type system.
  • Pony: explicit authority through object capabilities.
  • Daml: authorized operations and multi-party workflows.
  • Temporal: deterministic replay and durable workflows.

This is a comparison of mechanisms, not a claim that no earlier system combines them.

Could Edict generate Lean proofs?

RESEARCH DIRECTION

Yes, in principle: translate a supported Core subset into formal definitions, generate proof obligations, and have Lean check completed proofs.

A useful first target is a bounded byte slice. The proof should establish that the exact modeled operation respects its range and output bounds.

The translator must preserve Edict's meaning. The theorem must refer to the expected operation and assumptions. Exporting a Lean file alone proves nothing.

This is proposed work, not an implemented Edict exporter. Read about Lean proof validation ↗

What should I not assume?

Do not assume every parsed feature compiles, every compiled artifact runs, or every valid operation has permission.

The current subset is deliberately restricted. Host code, target implementations, external adapters, and their assumptions remain part of the system's trust boundary.

Start with a version-pinned example. Expand only when its compiler and runtime both support the required behavior.
